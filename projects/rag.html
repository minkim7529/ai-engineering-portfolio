RAG (Retrieval-Augmented Generation)

LLM이 모르는 내용, 최신 내용, 우리 조직만의 내용을 "검색해서 알려주는" 방법 — 원 논문부터 실무 파이프라인까지 정리

원 논문 보기 (Lewis et al., 2020) → 개인 학습 정리
  • Retrieval
  • Embeddings
  • Vector Search
  • Prompt Augmentation
  • Evaluation

RAG란 무엇인가

LLM은 학습 시점 이후의 정보를 모르고(지식이 고정됨), 학습 데이터에 없는 사내 문서·개인 데이터는 애초에 알 수 없으며, 모르는 내용도 그럴듯하게 지어내는 환각(hallucination) 문제가 있습니다. RAG는 이 문제를 모델을 다시 학습시키는 대신, 질문에 답하기 직전에 관련 문서를 검색해서 프롬프트에 함께 넣어주는 방식으로 우회합니다. 모델의 파라미터에 저장된 지식(parametric memory)에, 검색으로 가져온 외부 지식 (non-parametric memory)을 그때그때 더해주는 것이 핵심 아이디어입니다.

  • 최신성 — 모델을 재학습하지 않아도 문서만 갱신하면 최신 정보를 반영
  • 근거 제시 — 어떤 문서를 참고해 답했는지 출처를 함께 보여줄 수 있음
  • 환각 감소 — "문서에 없으면 모른다고 답하라"는 지시로 근거 없는 생성을 줄임
  • 비용 — 파인튜닝 없이 프롬프트 엔지니어링만으로 도메인 지식을 주입

핵심 아이디어 — 원 논문 (Lewis et al., 2020)

RAG라는 용어는 Meta AI(당시 Facebook AI Research)의 "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks" (NeurIPS 2020)에서 처음 제안됐습니다. 구조는 두 부분으로 나뉩니다.

  • Retriever — DPR (Dense Passage Retrieval) — 질문과 문서를 각각 별도의 BERT 인코더로 벡터화(bi-encoder)한 뒤, 벡터 내적으로 관련 문서 top-k를 검색합니다. 키워드 일치가 아니라 의미로 검색한다는 게 핵심입니다.
  • Generator — BART — 검색된 문서와 질문을 이어붙여 seq2seq 모델인 BART에 입력하고 답을 생성합니다. 논문은 이를 두 가지 방식으로 결합하는데, RAG-Sequence는 문서 하나를 골라 답 전체를 생성하고 여러 문서의 결과를 다시 종합하는 방식이고, RAG-Token은 매 토큰을 생성할 때마다 여러 문서의 확률을 함께 반영하는 더 세밀한 방식입니다.
  • End-to-end 학습 — 원 논문에서는 retriever와 generator를 함께 미세조정합니다. 반면 요즘 실무에서 쓰는 RAG는 대부분 retriever· generator를 따로 학습된 기성 모델을 그대로 조합해서 쓰는 "학습 없는(training-free)" 형태로 단순화되어 있습니다 — 아래 "현대적 RAG 파이프라인"이 바로 그 형태입니다.

현대적 RAG 파이프라인

실무에서 쓰는 RAG는 크게 색인 준비(미리 한 번)와 질의 응답(질문이 들어올 때마다) 두 단계로 나뉩니다.

왜 벡터 검색이 되는가 — 임베딩과 유사도

임베딩 모델은 문장을 고차원 벡터로 바꾸는데, 이때 의미가 비슷한 문장은 벡터 공간에서 가까운 위치에 놓이도록 학습되어 있습니다. 그래서 질문 벡터와 문서 벡터 사이의 거리(보통 코사인 유사도)를 재는 것만으로 "글자가 겹치는 문서"가 아니라 "의미가 통하는 문서"를 찾을 수 있습니다.

핵심 구성요소

1. 청크 분할 (Chunking)

문서를 통째로 임베딩하면 너무 뭉뚱그려져 검색 정확도가 떨어지고, 너무 잘게 쪼개면 문맥이 끊깁니다. 보통 500~1,000 토큰 단위로 자르되, 문장이나 단락 경계를 존중하고(무작정 글자 수로 자르지 않고) 청크 사이에 10~20% 정도 겹치는 구간(overlap)을 두어 경계에서 문맥이 잘리는 걸 막습니다.

2. 임베딩 모델

모델특징
OpenAI text-embedding-3API 호출형, 다국어 지원 우수, 별도 서빙 불필요
BAAI/bge-m3오픈소스, 100개 이상 언어 지원, 한국어 성능 좋음, 로컬 서빙 가능

종류특징

코드로 보는 최소 RAG 파이프라인

라이브러리 하나로도 구현할 수 있지만, 무슨 일이 일어나는지 보이도록 검색과 프롬프트 구성을 직접 푼 최소 예시입니다.

minimal_rag.py — 임베딩 검색 + 프롬프트 구성 
from sentence_transformers import SentenceTransformer
import faiss
import numpy as np

embedder = SentenceTransformer("BAAI/bge-m3")

documents = [
    "환불은 결제일로부터 7일 이내에만 가능합니다.",
    "배송은 평균 2~3영업일이 소요됩니다.",
    "회원 등급은 최근 12개월 구매 금액 기준으로 매월 갱신됩니다.",
    # ... 실제로는 문서를 청크 단위로 잘라 수백~수만 개를 넣는다
]

# 1) 색인 준비 — 문서를 벡터로 변환하고 인덱스에 저장 (미리 한 번만 실행)
doc_embeddings = embedder.encode(documents, normalize_embeddings=True)
index = faiss.IndexFlatIP(doc_embeddings.shape[1])  # 정규화된 벡터 + 내적 = 코사인 유사도
index.add(np.array(doc_embeddings, dtype="float32"))


def retrieve(query: str, k: int = 3) -> list[str]:
    """질문과 가장 유사한 문서 top-k를 반환한다."""
    q_emb = embedder.encode([query], normalize_embeddings=True)
    scores, idxs = index.search(np.array(q_emb, dtype="float32"), k)
    return [documents[i] for i in idxs[0]]


def build_prompt(query: str, contexts: list[str]) -> str:
    context_block = "\n\n".join(f"[{i+1}] {c}" for i, c in enumerate(contexts))
    return f"""다음 문서를 참고해서 질문에 답하세요. 문서에 없는 내용은
"제공된 정보로는 알 수 없습니다"라고 답하세요.

{context_block}

질문: {query}
답변:"""


query = "환불 받으려면 언제까지 신청해야 하나요?"
contexts = retrieve(query)
prompt = build_prompt(query, contexts)
# response = llm.generate(prompt)  # 실제 LLM 호출 (OpenAI, Gemini, Ollama 등)
포인트 — 색인(index.add)은 문서가 바뀔 때만 다시 실행하면 됩니다. 질문마다 매번 다시 계산하는 건 retrieve부터입니다. 실무에서는 이 구조를 그대로 두고 청크 분할·리랭킹·평가 단계만 덧붙이는 경우가 많습니다.

검색 품질을 높이는 기법들

기법설명
하이브리드 검색벡터 검색(의미) + BM25 키워드 검색(정확한 용어·숫자·고유명사)을 함께 써서 서로의 약점을 보완
리랭킹 (Reranking)1차로 top-50 정도를 빠르게 벡터 검색한 뒤, 더 무겁지만 정확한 cross-encoder로 재정렬해 최종 top-k만 남김
HyDE질문을 바로 검색하는 대신, LLM이 먼저 "가상의 답변"을 생성하고 그 답변으로 검색 — 질문보다 답변이 문서와 어휘적으로 더 비슷하다는 점을 이용
쿼리 재작성 / 멀티쿼리모호하거나 짧은 질문을 LLM으로 구체화하거나, 하나의 질문을 여러 관점으로 확장해 각각 검색 후 합침
메타데이터 필터링날짜·카테고리·권한 같은 메타데이터로 검색 범위를 먼저 좁혀 정확도와 속도를 함께 개선

고급 RAG 아키텍처

방식핵심 아이디어
Self-RAG검색이 필요한지, 검색된 문서가 실제로 도움이 되는지를 모델 스스로 판단하며 생성 (Asai et al., 2023)
Corrective RAG (CRAG)검색 결과의 품질을 평가해 낮으면 웹 검색 등 다른 소스로 보정 (Yan et al., 2024)
GraphRAG문서를 지식 그래프로 구조화해, 개별 문서 검색으로는 답하기 어려운 "전체를 요약·연결해야 하는" 질문에 대응 (Edge et al., 2024)
Agentic RAGLLM이 필요에 따라 검색을 여러 번 반복하거나 다른 도구(계산기, API 등)와 함께 검색을 하나의 행동으로 다룸

RAG 평가 방법

"그럴듯해 보이는 답"과 "실제로 문서에 근거한 답"은 다릅니다. RAGAS (Es et al., 2023) 같은 프레임워크는 사람이 일일이 채점하지 않고도 LLM을 채점자로 활용해 아래 지표를 자동 측정합니다.

  • Faithfulness(충실도) — 답변의 각 주장이 검색된 문서에서 실제로 뒷받침되는가
  • Answer Relevancy(답변 관련성) — 답변이 질문의 의도에 실제로 맞는가
  • Context Precision(문맥 정밀도) — 검색된 문서 중 실제로 답변에 쓸모 있었던 비율
  • Context Recall(문맥 재현율) — 정답을 만드는 데 필요한 정보가 검색 결과에 빠짐없이 있었는가
한계 — RAG는 "검색이 잘 됐을 때"만 잘 작동합니다. 문서 자체에 답이 없으면 아무리 좋은 LLM도 답할 수 없고, 청크 분할이 어색하면 맥락이 끊긴 채로 검색되어 오히려 오답을 만들 수 있습니다. 또한 검색 단계가 추가되는 만큼 지연 시간(latency)이 늘고, 리랭킹·멀티쿼리 같은 기법을 더할수록 비용도 함께 늘어나는 트레이드오프가 있습니다.

헷갈리기 쉬운 포인트

파인튜닝과 RAG는 서로 대체재가 아니라 다른 문제를 풉니다. 파인튜닝은 "모델이 특정 스타일·형식으로 답하게" 만드는 데 적합하고, RAG는 "모델이 모르는 최신·비공개 지식을 알게" 만드는 데 적합합니다. 실무에서는 둘을 함께 쓰는 경우가 많습니다(예: 답변 형식은 파인튜닝으로, 근거 지식은 RAG로). 또 하나 헷갈리기 쉬운 지점은 "임베딩 유사도가 높다"가 "정답이다"를 보장하지 않는다는 것입니다 — 유사도는 의미적으로 가깝다는 뜻이지, 질문에 대한 정답을 담고 있다는 보장은 아니라서 리랭킹·평가 단계가 따로 필요합니다.

실무에서 자주 겪는 문제와 대응

증상흔한 원인대응
검색은 됐는데 답이 엉뚱함청크가 너무 커서 관련 없는 내용까지 섞여 들어감청크 크기를 줄이고 overlap 조정, 리랭킹 추가
분명 있는 내용인데 검색이 안 됨질문과 문서의 표현 방식이 달라 임베딩 유사도가 낮음(어휘 격차)하이브리드 검색(BM25 병행), 쿼리 재작성/HyDE 적용
숫자·고유명사가 자꾸 틀림의미 기반 벡터 검색은 정확한 수치·이름 매칭에 약함키워드 검색을 병행하거나 메타데이터 필드로 별도 필터링
답변 속도가 느림top-k를 과도하게 크게 잡거나 리랭킹 모델이 무거움1차 검색 k를 줄이고, 가벼운 리랭커로 교체하거나 캐싱 도입
