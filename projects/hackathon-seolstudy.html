설스터디

블레이버스 제4회 MVP 개발 해커톤 — 멘토와 함께하는 수능 국어·영어·수학 학습 코칭 플랫폼

개요

설스터디는 수능 국어·영어·수학 학습을 위한 1:1 멘토링 기반 학습 코칭 플랫폼입니다. 멘토가 직접 설계하는 맞춤형 학습 플랜, 일일 플래너·자기체크·공부 시간 추적으로 실행력을 높이고, 과목별 피드백과 주기별 보고서로 관리 품질을 표준화하는 것을 핵심 가치로 삼았습니다. 6인 팀("세미콜론": 이승민·공지호·구승율·김민석·김태희·조현빈)으로 블레이버스 제4회 MVP 개발 해커톤에 출품해 본선에 진출했으며, 본인 담당은 프론트엔드입니다.

진행 과정

수능을 준비하는 고등학생 페르소나의 학습 여정을 계획 → 공부 → 시험 → 결과 확인 → 오답 풀이 단계별로 매핑하고, 각 단계의 pain point에서 기능을 도출하는 방식으로 기획했습니다. 이후 멘티 화면(모바일 최적화)과 멘토 화면(PC 최적화)을 라우트 단위로 분리해 병렬로 개발했습니다. 프론트엔드는 app/mentee, app/mentor 두 디렉터리로 나누고, 공통 컴포넌트·Zustand 스토어·API 훅을 별도 레이어로 분리해 두 화면이 로직을 공유하도록 구성했습니다.

주요 기능

  • 멘티(학생) — 일일/주간/월간 플래너(오늘의 할 일·자기체크·주간 통계·월간 캘린더), 과목별 공부 시간 타이머, 과제 제출(이미지 업로드), 일일·주간·월간 피드백 열람, 학습 보고서 및 추이 분석, 스트릭·히트맵 기반 학습 패턴 시각화, 멘티 간 달성률 랭킹, 학습 리마인더 알림
  • 멘토(선생님) — 담당 멘티 목록 및 대시보드, 멘티별 플래너·스트릭· 히트맵·통계 조회, 학생별 맞춤 과제 생성/수정/승인, 제출물 코멘트, 칼럼·PDF 학습지 업로드, 과목별 상세 피드백 작성, 멘티별 보고서 열람

담당 구현 — 프론트엔드

Next.js 16 App Router와 React 19, TypeScript로 멘티/멘토 화면을 구현했습니다. 서버 상태(플래너, 피드백, 보고서 등 API 데이터)는 TanStack Query로 캐싱·재검증하고, 클라이언트 상태(UI 토글, 폼 임시 입력값 등)는 Zustand로 분리해서 관리했습니다. 학습지·피드백처럼 서식이 필요한 입력에는 Tiptap 리치 텍스트 에디터를 붙였고, 폼 검증은 React Hook Form + Zod 스키마로 처리했습니다. TailwindCSS v4로 모바일(멘티)·PC(멘토) 두 레이아웃을 반응형으로 스타일링하고, Framer Motion으로 플래너 전환·랭킹 갱신 같은 인터랙션에 애니메이션을 더했습니다.

lib/api.ts — 로컬/프로덕션 API 엔드포인트 자동 판별 
// 로컬 개발 환경에서는 로컬 백엔드를 확인하고, 프로덕션에서는 Railway 사용
const PRODUCTION_API_URL = process.env.NEXT_PUBLIC_API_URL || 'https://semicolon-production.up.railway.app';
const LOCAL_API_PORT = process.env.NEXT_PUBLIC_LOCAL_API_PORT || '4000';

function isProduction(): boolean {
  if (typeof window === 'undefined') return false;
  const hostname = window.location.hostname;
  return hostname !== 'localhost' && hostname !== '127.0.0.1' && !hostname.startsWith('192.168.');
}

function getLocalUrl(): string {
  if (typeof window === 'undefined') return `http://localhost:${LOCAL_API_PORT}`;
  const hostname = window.location.hostname;
  return `http://${hostname}:${LOCAL_API_PORT}`;
}

async function checkLocalBackend(): Promise<boolean> {
  try {
    const controller = new AbortController();
    const timeoutId = setTimeout(() => controller.abort(), 1000);
    const response = await fetch(`${getLocalUrl()}/api/health`, {
      method: 'GET',
      signal: controller.signal,
    });
    clearTimeout(timeoutId);
    return response.ok;
  } catch (error) {
    return false;
  }
}
stores/useOverlayStore.ts — 다중 오버레이 상태 관리 (Zustand) 
import { create } from 'zustand';

interface OverlayStore {
  openOverlays: string[];
  setOverlay: (id: string, isOpen: boolean) => void;
  isOverlayOpen: boolean;
}

export const useOverlayStore = create<OverlayStore>((set) => ({
  openOverlays: [],
  isOverlayOpen: false,
  setOverlay: (id, isOpen) => set((state) => {
    const nextOverlays = isOpen
      ? Array.from(new Set([...state.openOverlays, id]))
      : state.openOverlays.filter(o => o !== id);
    return {
      openOverlays: nextOverlays,
      isOverlayOpen: nextOverlays.length > 0
    };
  }),
}));

느낀 점

해커톤이라는 제한된 시간 안에서 멘티(모바일)·멘토(PC) 두 화면을 동시에 완성해야 했기 때문에, 처음부터 공통 컴포넌트·Zustand 스토어·API 훅을 별도 레이어로 분리해 두 화면이 로직을 공유하도록 설계했습니다. 서버 상태와 클라이언트 상태를 TanStack Query· Zustand로 명확히 나눠 관리한 덕분에, 짧은 개발 기간에도 상태 관리가 꼬이는 일 없이 본선까지 안정적으로 기능을 확장할 수 있었습니다.

문제 해결

팀원들이 각자 로컬 백엔드를 켜둔 상태와 배포된 프로덕션 백엔드를 오가며 개발하다 보니, API 주소를 수동으로 바꿔가며 테스트하는 게 번거롭고 실수하기 쉬운 지점이었습니다. hostname으로 로컬/배포 환경을 자동 판별하고, 로컬 백엔드가 실행 중인지 헬스체크로 확인한 뒤 없으면 프로덕션(Railway)으로 자동 전환하는 유틸(lib/api.ts)을 만들어 팀원 전체가 같은 코드로 어떤 환경에서든 바로 개발을 이어갈 수 있게 했습니다.
